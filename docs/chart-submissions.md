# 譜面投稿・承認

## 利用者の操作

1. `/editor/`で作成・プレイ確認し、「譜面の投稿・管理」から制作者名・曲情報を入力して申請する。ログインは不要。申請前の編集は既存のブラウザ下書きで保持する。
2. 申請後は編集URLを控える。`/submissions/`には、このブラウザに編集用キーが残っている投稿を表示する。別端末では編集URLを開く。
3. 投稿内容を読み込み、エディターで変更して再申請できる。承認待ちの変更も可能。プレイ画面への切替時も編集画面を非表示で保持し、投稿情報・版番号・未申請の編集内容を維持する。版番号で競合を検出し、他の画面の変更を上書きしない。
4. 承認時は公開用のSongへ譜面TXT・解析済みデータ・YouTube URL・制作者名などを保存し、同じトランザクションで申請を削除する。編集URLは以後使えない。管理者が確認した版より更新されていたら承認は409で止まる。

制作者名は自己申告で本人確認ではない。編集URLは秘密情報で、知る人は修正できる。URLのキーはフラグメントに入れ、読み込み後にURLから除去し、APIにはAuthorizationヘッダーで送る。DBにはハッシュだけ保存する。自動的な再発行・本人確認による復旧はない。第三者へ共有しない。
公開後に誰でも修正案を投稿する機能は後日追加する。初期版では公開後の修正は管理者対応とし、以下の手順で新しい申請を公開曲へ紐付ける。ブラウザの投稿一覧は編集用キーの一覧のため、承認済みのリンクが残ることがあるが利用できない。

## 管理者の操作

`/admin/submissions/`でLDC専用の管理用キーを入力し、申請一覧から内容を開く。TXTの全文・ダウンロード・プレイプレビューで確認し、ゲームの曲番号を指定して承認する。プレビューは既存のプレイ機能と同じく歌詞ページを確認するもので、ポップ演出はTXTまたはゲーム側で確認する。却下しても公開済み版は残る。管理用キーは画面のメモリだけに保持する。

承認によってゲームへの組み込みや公開まで自動化するものではない。承認・ランキング登録の成功を確認してからゲームへ公開する。

### 承認の整合性

- ランキングへの仮登録は行わない。未承認の譜面はLDCだけに保存する。
- 曲番号・曲名・アーティスト・難易度の正式情報はランキングDB、譜面TXT・YouTube URL・制作者名はLDCが管理する。
- 初回承認で版と曲番号を固定し`publishing`にする。ランキングの既存の曲登録APIで登録が成功したら、同じトランザクションでLDCの公開Songを保存し、申請を削除する。承認済み申請や編集キーのハッシュはDBへ残さない。
- 承認は曲番号・修正対象の公開曲・申請ごとのDBロックを取り、ランキングAPIの呼び出しから公開保存・申請削除まで保持する。同じ申請の並行承認による重複送信を防ぐ。同じ曲の別申請が`publishing`の間は、その申請の再試行を先に完了し、別申請の承認を409で止める。
- 通信失敗・結果不明の場合は`publishing`を維持し、その間の編集・却下を禁止する。管理者が同じ版・曲番号で承認を再試行する。ランキング成功後にLDCが失敗しても、再試行で公開処理を完了できる。
- 新規・修正とも既存の`PUT /api/v1/admin/songs/{gameSongId}`を使う。投稿ID・版番号はLDC内だけで管理し、ランキングへ送信・保存しない。ランキング側のコード・DB変更は不要。
- 既存のランキングAPIはUPSERTのため、登録済み番号を指定するとその曲情報を更新する。曲番号の選択は管理者が確認する。ランキング側で古い版の再送を拒否する仕組みは追加しない。
- 修正版は同じ曲番号・同じ公開Songを更新する。既存の成績は残す。別譜面として分ける場合は新規投稿・別の曲番号とする。
- 承認待ちの間だけ公開版と申請中の版を分けて保持する。承認後は公開版だけを残す。全過去版の履歴・復元、Discord通知、自動ゲーム配信は初期実装に含めない。

## 投稿の制限

サーバーで本文を最大160KiB、TXTを128KiB、1000ページ・ポップ1000件、総時間3600秒までに制限する。YouTube URLはHTTPSの動画URLだけを受理し、正規URLへ変換する。任意のURLをサーバーから取得しない。

Turnstileはサーバーで成功・hostname・actionを検証し、未設定・検証エラー時は投稿を受け付けない。

PostgreSQLのトランザクションとadvisory lockを使って、複数のサーバーから同時投稿されても以下の上限を超えないようにする。

| 設定 | 初期値 | 対象 |
|---|---|---|
| `SUBMISSION_IP_DAILY_LIMIT` | 5 | 同じ接続元からの新規投稿・変更の合計／日本時間の1日 |
| `SUBMISSION_DAILY_LIMIT` | 50 | サイト全体の新規投稿・変更の合計／日本時間の1日 |
| `SUBMISSION_TOTAL_LIMIT` | 500 | 保存する申請の総件数。新規投稿だけを停止する |

申請が残っている間は、同じ成功結果の再送は件数を増やさない。承認後に同じ申請への閲覧・変更・承認を再送すると404になる。承認応答を受け取れなかった場合は、管理者が公開曲と申請一覧を確認する。接続元はVercelが上書きする`x-forwarded-for`を利用する。Vercel以外の本番環境では接続元の信頼設定を実装するまで受付を拒否する。開発・テスト環境だけローカルIPとして扱う。IPは秘密鍵付きハッシュで日ごとに集計し、期限切れカウンターは次の成功投稿時に削除する。IPの変更による回避はあり得るが、全体上限は有効。

上限はDB保存の増加を抑えるためのもので、HTTPリクエスト自体やTurnstile検証・関数実行を完全に止めるものではない。大量の不正アクセスへの対策はホスティング側のFirewall／Rate Limitingも併用する。承認済み申請は自動削除する。未承認・却下済み投稿の整理や容量確認は運用で行い、全体上限に達したら整理後に再開する。

歌詞・曲名・制作者名の記号はSQL文字列に連結せず、Prismaの値として渡す。画面はReactのテキスト描画を使い、投稿内容をHTMLとして実行しない。譜面TXTの装飾記法・文字制約は既存エディターの規則に従う。

## ランキングAPIとの連携

承認処理はLDCのサーバーから既存の`PUT /api/v1/admin/songs/{gameSongId}`を呼び出す。`RANKING_ADMIN_API_KEY`を`Authorization: Bearer <キー>`として付け、`Content-Type: application/json`で次の曲情報だけを送る。

```json
{"title":"架空の曲名","artist":null,"level":"5+"}
```

曲番号はURLで指定する。新規登録・既存曲の修正は同じAPIを使い、投稿ID・版番号・譜面本文・YouTube URL・制作者名は送らない。201 `created`、200 `updated`、200 `unchanged`を成功として扱う。応答の曲情報を確認してからLDCの公開処理を完了する。

通信タイムアウト後にランキング側の処理が継続する可能性まで、既存APIだけで完全に排除することはできない。結果不明時は別申請の承認を進めず同じ内容で再試行する。

LDCとランキングのDBをまたぐ1つのトランザクションはないため、ランキングへの登録が一時的に先行する場合がある。失敗時は上記の承認処理中の状態を維持し、同じ曲番号・本文で再試行する。

この呼び出しはサーバーから行うため、ランキング側のCORS変更は不要。公開曲一覧APIからの曲情報の取り込みは、この投稿・承認処理とは別の機能として扱う。

## 導入手順

1. 既存のランキング曲登録APIの管理用キーを用意する。ランキング側のデプロイ・DB移行は不要。
2. LDCのDBバックアップを取得したうえで、`npx prisma migrate deploy`を実行する。既存の曲はそのまま保持し、投稿関連のテーブル・列だけを追加する。
3. Turnstileで対象ホストを登録し、以下をVercelの環境変数へ設定する。
   - `NEXT_PUBLIC_TURNSTILE_SITE_KEY`：公開サイトキー（ビルド時に必要）
   - `TURNSTILE_SECRET_KEY`：秘密キー
   - `TURNSTILE_HOSTNAME`：`ldc.kayomodoki.com`（スキーム・パスなし）
   - `SUBMISSION_ADMIN_KEY`：LDC管理者専用の32文字以上のランダムな秘密情報
   - `SUBMISSION_RATE_SECRET`：接続元ハッシュ用の32文字以上のランダムな秘密情報
   - `RANKING_ADMIN_API_KEY`：ランキング側の管理用キー。公開変数へ入れない
4. 最後に`SUBMISSIONS_ENABLED=true`を設定して再デプロイする。未設定時は投稿不可。受付停止時は`false`に戻す。承認・閲覧は受付停止中も利用できる。
5. 架空の譜面で投稿・修正・却下・承認・ランキング登録を確認する。公開済み版が承認前に変わらないこと、再試行で重複しないことを確認する。

管理画面なしでも、同じAPIをHTTPクライアントから利用可能。管理者認証は`Authorization: Bearer <SUBMISSION_ADMIN_KEY>`。
- `GET /api/admin/submissions/`：承認待ち・承認処理中の一覧（20件。`cursor`で続き）
- `GET /api/admin/submissions/{id}/`：申請の全文・版番号
- `POST /api/admin/submissions/{id}/`：`{"action":"approve","revision":1,"gameSongId":"001"}`または`{"action":"reject","revision":1}`

管理キー・編集URL・投稿全文をアクセスログやエラー調査ログへ保存しない。

## 既存の取り込み済み曲を修正・再承認する場合

初回だけ管理者が対応関係を確認して紐付ける。曲名や制作者名の一致で自動的に編集権限を渡さない。

1. 制作者が元のTXTをエディターへ読み込み、修正して通常どおり新規申請する。
2. 管理者が申請内容、既存のLDC曲ID、ランキングのゲーム曲番号を確認する。以下のSQLの`投稿UUID`・`123`・`001`を確認した値に置き換える。実際の値や編集キーを公開リポジトリへ保存しない。
3. LDCのPostgreSQLで、公開済みの曲を申請の更新先として設定する。既存の公開譜面はまだ変更しない。同じ公開曲に複数の修正申請を紐付けられる。申請側の曲番号・公開曲IDは一意制約を設けず、公開曲の曲番号だけを一意にする。ランキング側での紐付け作業は不要。

```sql
UPDATE chart_submission SET "publishedSongId" = 123, "gameSongId" = '001'
WHERE id = '投稿UUID'::uuid AND status = 'pending'
  AND "publishedSongId" IS NULL AND "gameSongId" IS NULL
  AND EXISTS (SELECT 1 FROM song WHERE id = 123);
SELECT id, "publishedSongId", "gameSongId", status
FROM chart_submission WHERE id = '投稿UUID'::uuid;
```

4. 更新対象が1行で、曲の対応関係が正しいことを確認してから、LDC管理画面で申請を読み込み直して承認する。第1版が承認されると、既存のLDC曲を更新し、ランキング側も同じ曲・既存成績を維持する。申請は承認後に削除される。次に修正する場合も、新しい申請を作成して管理者が紐付ける。

`Song.submissions`はこの曲に対する申請の一覧、`ChartSubmission.publishedSong`は個々の申請の更新先である。各申請の更新先は1曲だが、1曲に複数の申請があるため1対多の関連になる。承認後は申請を削除するので、承認履歴が蓄積するものではない。

この初回紐付け専用の画面は実装しない。間違った曲同士を結び付けないよう、既存曲への紐付けは管理者の作業に限定する。
